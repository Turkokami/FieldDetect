ACE Study Guide

The Associate Cloud Engineer exam is practical: it rewards knowing which service solves which problem and the everyday gcloud / console workflows to deploy and operate them. This guide is organized by the five official domains.

1 Setting up a cloud solution environment

Resource hierarchy. Organization → Folders → Projects → Resources. IAM and Organization Policies set higher up are inherited downward. Folders group projects (e.g., per department) so policies apply to all projects inside.

Projects & billing. Every resource lives in a project. A project must be linked to a billing account — this is not automatic and is not inherited from a folder. A billing account can pay for many projects; a project has exactly one active billing account.

  • Create a project and link billing: 
    gcloud projects create my-proj --folder=FOLDER_ID
gcloud billing projects link my-proj --billing-account=XXXXXX-XXXXXX-XXXXXX
  • Budgets & alerts notify you as spend approaches a threshold (50/90/100%). Budgets do not stop resources by themselves — pair with a Pub/Sub topic + Cloud Function for automation.
  • Cloud SDK / gcloud CLI: install locally, then gcloud init to authenticate and pick a project. Cloud Shell is a browser terminal with tools pre-installed and pre-authenticated.
Exam tip: Configurations let you switch contexts fast — gcloud config set project, gcloud config configurations create/activate. Remember VMs are zonal, subnets are regional, and a VPC/network is global.

Location types: regional (one region), dual-region, and multi-region (broad geo, highest availability). Use lifecycle rules to auto-transition classes or delete objects.

Cost planning

  • Pricing Calculator — estimate cost before deploying.
  • Spot / Preemptible VMs — deep discount, can be reclaimed anytime → fault-tolerant batch.
  • Committed use discounts (CUD) — 1 or 3-year commitment for steady 24/7 usage → biggest steady-state savings.
  • Sustained use discounts — automatic, applied for running VMs a large share of the month.

Networking basics

  • VPC is global; subnets are regional. Auto mode makes a subnet per region; custom mode gives you full control.
  • Firewall rules: by protocol/port, source (CIDR / tags / service accounts), target (tags / SAs). Default-deny inbound, default-allow outbound.
  • Connect networks: VPC Peering (VPC↔VPC, non-transitive), Shared VPC (one host network shared to service projects), Cloud VPN (encrypted over internet), Interconnect (private, high-bandwidth to on-prem).

3 Deploying and implementing a cloud solution

Highest-weight, hands-on domain. Know the deploy commands and the operational building blocks.

Compute Engine

  • Create a VM: 
    gcloud compute instances create web-1 \
  --zone=us-central1-a --machine-type=e2-medium \
  --image-family=debian-12 --image-project=debian-cloud
  • Instance template → blueprint for identical VMs (image, machine type, startup script in metadata).
  • Managed Instance Group (MIG) → autohealing + autoscaling + rolling updates (maxSurge / maxUnavailable) from a template. Unmanaged groups = arbitrary VMs, no templating.
  • Persistent disks can be resized larger while attached (then grow the filesystem) — never shrunk. Snapshots = incremental backups; automate with a snapshot schedule (resource policy).

GKE

  • Get credentials for kubectl: 
    gcloud container clusters get-credentials my-cluster --region us-central1
  • Expose a workload: Service ClusterIP (internal), NodePort, LoadBalancer (external L4), or an Ingress (L7 HTTP(S) LB).
  • Autopilot manages nodes for you; Standard = you manage node pools.

Serverless

  • Cloud Run: 
    gcloud run deploy api --image=REGION-docker.pkg.dev/PROJ/repo/img:tag --region=REGION
  • App Engine: gcloud app deploy; supports multiple versions and traffic splitting for canary rollouts.
  • Schedule serverless work with Cloud Scheduler (managed cron) → HTTP / Pub/Sub / Cloud Run job.
  • Store images & packages in Artifact Registry (supersedes Container Registry).

Networking on deploy

  • Static external IP → stable public IP that survives VM recreation.
  • Cloud NAT → outbound-only internet for VMs without external IPs.
  • Private Google Access → reach Google APIs from VMs without external IPs.
  • Load balancers: global external Application LB (L7, one anycast IP, cross-region) vs. Network LB (L4, regional).

Data movement

gcloud storage cp -r ./localdir gs://my-bucket     # upload
gcloud storage cp gs://my-bucket/file .            # download
bq load DATASET.TABLE gs://bucket/data.csv         # into BigQuery

4 Ensuring successful operation

GoalTool
Metrics, dashboards, alerts (CPU/disk/network + custom)Cloud Monitoring
Search / route / retain logsCloud Logging
Aggregate & dedupe application errorsError Reporting
Latency & distributed request tracingCloud Trace
Probe availability from global locationsUptime checks
  • Ops Agent is needed on VMs for memory and custom/guest metrics (CPU/disk/network come by default).
  • Alerting policy = condition on a metric + notification channels (email, SMS, PagerDuty, Slack, Pub/Sub).
  • Log sinks route matching logs to BigQuery (analysis), Cloud Storage (cheap long-term retention), or Pub/Sub (streaming). Aggregated sinks at folder/org level centralize logs from many projects.
  • Quotas cap how much of a resource a project may use (CPUs, external IPs, API rate). Request increases in IAM & Admin → Quotas.
  • Backups: snapshots for disks (+ schedules); machine images capture a whole VM (all disks + config).

5 Configuring access and security

IAM building blocks

Who (principal) → can do what (role = bundle of permissions) → on which resource.

Role typeNotes
Basic (Owner/Editor/Viewer)Broad, legacy — avoid for least privilege.
PredefinedService-specific, curated by Google (e.g., roles/storage.objectViewer). Preferred default.
CustomYour chosen permission set, at org or project level. Use when no predefined role fits.
  • Least privilege is the guiding principle. Grant to groups, not individuals, for scale.
  • IAM deny policies are evaluated first and override allow grants.
  • View a project's policy: 
    gcloud projects get-iam-policy PROJECT_ID
  • Add a binding: 
    gcloud projects add-iam-policy-binding PROJECT_ID \
  --member="group:devs@example.com" --role="roles/compute.viewer"

Service accounts (SAs)

  • Attach an SA to a VM and grant it minimal roles → app gets short-lived creds from the metadata server. Avoid downloaded JSON keys.
  • roles/iam.serviceAccountUser → act as an SA (e.g., deploy a VM that runs as it).
  • roles/iam.serviceAccountTokenCreator → impersonate / mint short-lived tokens.
  • Leaked key? Disable/delete the key immediately, then rotate. Prefer Workload Identity.

Security & governance

  • Organization Policy constraints enforce config rules org-wide (e.g., compute.vmExternalIpAccess to ban external IPs). IAM = who can act; Org Policy = what's allowed.
  • Cloud Audit Logs: Admin Activity (always on — who changed what), Data Access (opt-in), System Event, Policy Denied.
  • Secret Manager for passwords/keys — encrypted, versioned, IAM-controlled.
  • Encryption at rest is on by default (Google-managed). Use CMEK (Cloud KMS) to control/rotate your own keys.
  • OS Login ties SSH access to IAM identities instead of per-VM key management.

Exam-day tips

  • Least privilege wins. When two roles both work, pick the narrower one.
  • Managed > DIY. Prefer the managed/serverless option unless the question demands OS-level control.
  • Match scope to resource: VM = zonal, subnet = regional, VPC = global.
  • Watch the keywords: "scale to zero" → Cloud Run/App Engine std; "global relational + strong consistency" → Spanner; "interruptible batch, cheapest" → Spot VMs; "who did what" → Admin Activity audit logs.
  • Read multi-select counts. "Choose two" means exactly two.
  • Flag-and-return: don't burn time on one item; ~2.2 min/question average.
